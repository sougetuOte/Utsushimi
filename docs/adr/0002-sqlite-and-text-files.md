# 0002. 会話と記憶は SQLite に1発言ごとにコミットし、人格の根っこはテキストファイルに置く

- 日付：2026-09-23
- 状態：提案
- 決めた人：主人

## 背景

禁則「記憶を失わない。会話は即時に永続化し、異常終了や電源断でも失わない」（`CLAUDE.md` §0）。
記憶は3層で文脈に入る：Hot（人格の根っこ・主人について・口調の見本・いまの会話）、Warm（直近の日記）、Cold（会話断片を必要なときに検索）
（`docs/concept.md` §4.1）。断片は数か月で数万件になる（§4.7）。
一方で、主人が書ける部分と書けない部分を分ける（保護指定4）。凍結した根っこは AI が書き換えず、主人の手だけが変えられる（BH-19）。
主人が手で書き換えたらキャラの側が気づく（BH-21）。

## 決定

- **会話断片・日記・主人についての記録・その変更履歴は SQLite 1ファイル**に置く。WAL・`synchronous=FULL`、**1発言ごとにコミット**する。
  検索は FTS5（trigram 分割）。Python 標準の `sqlite3` を使う。
- **人格の根っこ（C1〜C11）と口調の見本（S1〜S7）は、UTF-8 のテキストファイル**に置く。本体は凍結後これを読むだけで、書く口を持たない。
  凍結したときの内容のハッシュを SQLite に控え、起動のたびに比べて、主人の手による変更に気づく。
- 置き場は `data/`（git に載せない。D6）。

## 結果

- S4（`taskkill /F` の直後にも1発言が残る）と S6（2回目の起動で前回を読む）は、この形で3候補とも可だった。
- FTS5 の trigram 分割で、日本語の部分一致（「話の続」→「昨日の話の続き」）が標準の `sqlite3` で引けた（実行して確かめた）。追加の依存は要らない。
- 根っこがテキストなので、主人はエディタで読めて書ける。本体側に「根っこを書く関数」が存在しないことで、禁則をコードの形で担保できる。
- 引き受けるもの：
  - **電源断は測っていない。**`synchronous=FULL` の WAL はコミットごとに同期書込みをする、という SQLite の仕様に頼る
  - 根っこ（ファイル）と記憶（DB）の2か所になる。バックアップと引っ越しは2つを揃えて扱う
- 後で効く縛り：意味検索（ベクトル）を足すなら、別の索引を SQLite の外か拡張で持つことになる。

## 却下した案

| 案 | 理由 |
|---|---|
| すべてテキスト（JSONL・Markdown） | 追記だけなら即時保存はできるが、検索・日付での欠け補完・変更履歴を自前で書くことになる |
| すべて SQLite（根っこも DB の中） | 主人が手で読めない・書けない。保護指定4（書ける所と書けない所を分ける）を画面の機能で作ることになり、段1が太る |
| ベクトル DB を最初から持つ | 段1の「覚えている」はキーワード検索で足りる（前身も Phase 1 は素のキーワード検索。`docs/concept.md` §4.2）。迷ったら足さない |

## 消滅条件

- 断片が増えて、検索が応答の待ちに効くほど遅くなったと実測で分かったら見直す
- 意味検索が要る段（段3〜4）に入ったら、索引の置き場を見直す
